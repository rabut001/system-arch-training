# 解説の見直し

午前Ⅱの解説文を、肢ごとに直して確認する作業の手順である。進捗は、問題文の抽出と解説の見直しで別のチェックリストにして管理する。

## 現在地

令和7年度春期、令和6年度春期、令和5年度春期、令和4年度春期、令和3年度春期、令和元年度秋期、平成30年度秋期、平成29年度秋期、平成28年度秋期、平成27年度秋期、平成26年度秋期の問題文25行と解説100行は確認済みである。残りの回のチェックリストはまだ作っていない。初回の確認で、名前だけの肢には意味を書くこと、最大または最小を選ぶ計算は各肢の結果を書くことを、この文書の観点に入れてある。

画面の出題はこれまでどおり問題画像のままとする。この作業で製品の仕様を変えるときは、先に `AGENTS.md` を更新する。

## 目的

既存の解説を、選択肢の言い換えで終わらせず、用語・仕組み・誤りの理由が分かる文にする。公式資料に解説はない。直した文は `data/<回の id>.json` の `explanation` に保存する。実行時には生成しない。

## 対象

16回、各25問、各問のア〜エである。問題文の抽出は問ごとで、全体では 400 行になる。解説の見直しは肢ごとで、全体では 1,600 行になる。

最初に実施するのは令和7年度春期（`2025-r07-haru`）の1回分である。問題文 25 行と解説 100 行の確認が終わり、問題文の起こし方、解説の書き方、チェックリストの回し方に問題がなければ、残り15回を一つの範囲として一気に進める。問題があったときは、この文書の手順を直してから残りに進む。

## 問題文の抽出

解説を直す前に、その範囲の問題文を `data/<回の id>.json` の各問へ足す。問題冊子はページ全体が画像なので、画像から一度起こし、画像と照合してから保存する。進捗は `text/<回の id>.json` で、問ごとに管理する。ファイルは作業を始める回の分だけ作る。いま置いてあるのは令和7年度春期、令和6年度春期、令和5年度春期、令和4年度春期、令和3年度春期、令和元年度秋期、平成30年度秋期、平成29年度秋期、平成28年度秋期、平成27年度秋期、平成26年度秋期である。残りの回は、その回の作業を始めるときに作る。`data/` へは置かない。

各問に次を足す。

| 項目 | 内容 |
| --- | --- |
| `stem` | 設問文。表がある問は、表の中身も Markdown の表でここに書く |
| `choices` | ア、イ、ウ、エの本文。肢が表のときは、その表も Markdown の表で書く |
| `visuals` | 文章だけでは表せない要素。`figure`（図・グラフ）、`table`（表）、`image`（図でも表でもない画像）。複数同時にあってよい。該当がなければ空配列 |

図そのものは文字にしない。`visuals` に `figure` または `image` がある問は、見直しとレビューのときに問題画像を開く。表は `stem` または `choices` に Markdown の表で書き、`visuals` には `table` を残す。セルの結合や、一つのセルの中の複数行は Markdown では表せない。その表は、結合している範囲を文で補って書く。

`no`、`answer`、`image` は変えない。既存の項目で直すのは `explanation` だけである。

`data/` はビルド時にサイトへコピーされる。問題文のテキストも公開データに含まれる。画面には出さない。項目を足す前に、`AGENTS.md` の「問題文のテキスト化はしない」を、データには持ち画面には出さない、という記述へ更新する。

各行の項目は次のとおり。

| 項目 | 内容 |
| --- | --- |
| `no` | 問番号（1〜25） |
| `status` | `未着手`、`抽出済み`、`要見直し`、`確認済み` |
| `comments` | 抽出側とレビュー側のやり取り。要素は `role`（`抽出` または `レビュー`）と `text` |

コメントは追記する。過去の文は消さない。起こした本文は問題 JSON にだけ置き、チェックリストには複製しない。

### 状態

- `未着手` … まだ起こしていない。
- `抽出済み` … 抽出側が問題 JSON へ入れ終わり、レビュー待ち。
- `要見直し` … レビューが画像と一致しないと判断した。
- `確認済み` … レビューが画像と一致すると判断した。

### ループ

抽出とレビューは別の作業にする。起こした同じ手番で、その行を `確認済み` にしない。

1. 行がなければ作り、状態は `未着手` にする。
2. `stem`、`choices`、`visuals` を問題 JSON に入れる。その問を `抽出済み` にする。抽出側のコメントには、図・表・画像の判断と、文字の読みで迷った点を書く。
3. `抽出済み` の行だけを、問題画像と照合してレビューする。
4. 観点を満たす行は `確認済み` にする。足りない行は `要見直し` にし、レビュー側のコメントに観点の番号と理由を書く。
5. `要見直し` の行だけを直し、`抽出済み` に戻してレビューへ出す。
6. 範囲内の行がすべて `確認済み` になるまで、4と5を繰り返す。

この確認が終わるまで、その範囲の解説には入らない。

### 確認の観点

1. `stem` が、図と表以外の設問文と一致する。
2. `choices` のア〜エが、画像の各肢と一致する。肢の取り違えがない。
3. 表は Markdown の表にして `stem` または `choices` に含め、`visuals` に `table` を入れる。セルの結合や、一つのセルの中の複数行は、結合している範囲を文で補っている。
4. 図・グラフは文字にせず、`visuals` に `figure` を入れる。図でも表でもない画像は `image` とする。該当がなければ `visuals` は空配列である。
5. `no`、`answer`、`image` は変えない。

折り返しの改行は、文のつながりが分かる形に詰めてよい。句読点と用語の文字は画像に合わせる。

## 解説のチェックリスト

回ごとに `checklist/<回の id>.json` を置く。`data/` へは置かない。状態とコメントをサイトへ出さないためである。ファイルは、作業を始める回の分だけ作る。いま置いてあるのは令和7年度春期、令和6年度春期、令和5年度春期、令和4年度春期、令和3年度春期、令和元年度秋期、平成30年度秋期、平成29年度秋期、平成28年度秋期、平成27年度秋期、平成26年度秋期である。残りの回は、その回の作業を始めるときに作る。

各行の項目は次のとおり。

| 項目 | 内容 |
| --- | --- |
| `no` | 問番号（1〜25） |
| `choice` | ア、イ、ウ、エ |
| `status` | `未着手`、`見直し済み`、`要見直し`、`確認済み` |
| `comments` | 修正側とレビュー側のやり取り。要素は `role`（`見直し` または `レビュー`）と `text` |

正解の肢は、問題 JSON の `answer` で判別する。チェックリストには複製しない。

### 状態

- `未着手` … まだ直していない。
- `見直し済み` … 修正側が直し終わり、レビュー待ち。
- `要見直し` … レビューが観点を満たさないと判断した。
- `確認済み` … レビューが観点を満たすと判断した。

## 範囲の進め方

範囲は二つである。先の範囲がすべて `確認済み` になってから、次の範囲に進む。

1. 初回の範囲は、令和7年度春期の25問である。先に問題文の25行をすべて `確認済み` にする。続いて解説の100行がすべて `確認済み` になるまで、次の節のループを回す。
2. 初回を確認し、手順に問題がなければ、残り15回の二つのチェックリストを作り、15回分を一つの範囲として同じ順で進める。各範囲で、問題文の確認が済んでから解説に入る。
3. 初回に問題があったときは、手順をこの文書で直す。直した手順で初回を片付けてから、残り15回へ進む。

## 1範囲のループ

修正とレビューは別の作業にする。直した同じ手番で、その行を `確認済み` にしない。

1. その範囲の問題文がすべて `確認済み` であることを確認する。解説の行がなければ作り、状態は `未着手` にする。
2. その範囲の解説を直す。直した肢を `見直し済み` にする。修正側のコメントには、足した用語と、断定を避けた点を書く。元の解説の1.5倍以上になるときは、長くした理由も書く。
3. `見直し済み` の行だけをレビューする。問題文と解説を照らす。`visuals` がある問は問題画像も見る。元の1.5倍以上になっているときは、コメントの理由が妥当かも確認する。
4. 観点を満たす行は `確認済み` にする。足りない行は `要見直し` にし、レビュー側のコメントに観点の番号と理由を書く。
5. `要見直し` の行だけを直し、`見直し済み` に戻してレビューへ出す。
6. 範囲内の行がすべて `確認済み` になるまで、4と5を繰り返す。

一つの `explanation` に4肢の文が入っている。`要見直し` を直すときは、その肢の文だけを変える。ほかの肢の文まで変えた場合は、その肢の状態を `見直し済み` に戻す。

## レビューの観点

元の解説をそのまま残すことは優先しない。誤りと説明不足は直す。新しく足す説明は、根拠を確認できたものだけ書く。

1. 問題文の言い換えだけで終わらせない。用語の意味、仕組み、背景、具体例のうち、正誤の理由に必要なものを書く。問題文に書いてあることや、問題文から容易に想像できる説明は、繰り返さない。問題文と関係のない事項は書かない。
2. 各肢に対応する一般的な用語、契約形態、技術、理論があれば、それを特定して特徴や仕組みを書く。問題文から想像できる特徴は繰り返さない。肢の本文が用語の名前だけのときは、その意味を短く書く。複数の誤りの肢が同じ点で食い違うときも、それぞれの意味は書く。意味が問題文やその肢の本文にすでに書いてあるときは、名前を特定するだけで繰り返さない。
3. 肢全体に対応する一般的な概念がなければ、その旨を書く。記述の一部が既存の概念に似ているときは、類似点と相違点を書く。
4. 誤りの肢は、どの記述が、どの概念のどの特徴と食い違うかを書く。必要なときは短い事例や数値を使う。計算問題で、問う値が一つに定まるときは、正解の計算だけを書く。誤答の解説は書かない。最も大きくなるもの、または最も小さくなるものを選ぶ問は、正解の計算だけではどれが正解か分からない。各肢の結果を書くか、式にして最大または最小を求める。誤りの肢には、その計算結果以外の解説は書かない。
5. 用語、制度、契約の説明が正確かを確認する。似た概念を混同しない。一般的な傾向を、例外のない規則として書かない。法令や契約条件で扱いが分かれるときは、その違いを踏まえる。根拠を確認できないときは断定しない。
6. 長さは元の解説と同程度にする。残すのは、正解の根拠、誤りの理由、用語や概念の理解に必要な情報である。元の1.5倍以上になるときは、修正側がコメントに理由を書く。レビュー側は、その理由が妥当かを確認する。肢が名前だけで、意味が問題文に無いために長くなったときは、その旨を理由にする。各肢の結果を比べるために長くなったときも、その旨を理由にする。

問14は、この観点の見本にする。

ラボ契約は、一定以上の発注を約束する代わりに、スキルや人数の基準を満たす要員をベンダーが確保する契約である。イが正解である。アの「担当者の指名」と「直接の指揮命令」を両立する契約形態は、一般的なものでは見当たらない。紹介予定派遣は該当するが、あまり一般的ではない。ウはレベニューシェアの説明である。エは実稼働だけの精算で、通常一定以上の発注が前提となるラボ契約には一致しない。

見本の事実関係も、観点5に従って確認する。見本の文をそのまま各問へ流用しない。見本のウは、肢の本文がすでにレベニューシェアの中身を書いているので、名前だけにしている。肢が名前だけの問に、この書き方を使わない。
