## アシスタント

hook の戻り値だけでは、自動実行モードでセッションの可否確認を出す方法はありません。

`permission: "ask"` は、Allowlist と Run Everything では「Hook requested approval」の確認になります。自動実行モードでは、Auto-review が実行してよいと判断したコマンドについて、この `ask` は無視されます。Cursor の開発元もこの挙動を認めていて、修正時期は示されていません。

自動実行モードで確実に効くのは `deny` だけです。これは可否確認ではなく、その場で実行を止めるものです。止めたあとエージェントが同じ `git push` をやり直しても、hook が再び拒否します。

`.cursor/permissions.json` の `autoRun.block_instructions` は、Auto-review に「確認へ回してほしい」と伝えるヒントです。公式には強制ではなく、分類器が優先すれば確認なしで実行されます。

今の hook は、セッション確認が出るモード向けの `ask` のままにしています。

## アシスタント

sh/bash の git hook で、`git push` 自体を止めることはできます。Cursor のセッションに可否確認を出すことは、この方法ではできません。

仕込む場所は、リポジトリの `pre-push` hook です。Git for Windows に付く bash でも、Linux の sh でも、同じスクリプトが動きます。`git push` が始まる直前に hook が動き、終了コードが 0 以外なら転送は行われません。Cursor の自動実行モードとは無関係です。

確認は、制御端末 `/dev/tty` へ出します。

```sh
printf 'git push を実行しますか? [y/N] ' >/dev/tty
IFS= read -r answer </dev/tty || exit 1
```

端末がある実行では、ここで入力を待ちます。端末が無い実行では `/dev/tty` を開けないので、確認できたことにせず終了コード 1 で拒否します。エージェントの自動実行はこちらの経路になることが多く、その場合は push されません。

この hook を通らない実行もあります。`git push --no-verify` と、`git -c core.hooksPath=... push` は `pre-push` を呼びません。通常の `git push` は止まります。
